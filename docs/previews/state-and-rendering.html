01 · the foundation implemented · on device

Lazy top-down render

Chuks used to build the Node tree bottom-up and eagerly — children finished before their parent existed, so a component never knew its position. That single fact blocked automatic per-instance state. Now components are lazy descriptions the reconciler calls top-down, so each one knows its identity before it runs. This is the React-fiber / Flutter-Element / SwiftUI-identity model, native to Chuks.

THE LOOP, ONCE PER EVENT

event → dispatch → reduce/setState → render() re-runs the visible tree → reconcile diffs it → only the changed lines patch the native UI. Rebuilding is plain function calls; the diff keeps the platform work minimal.

WHY IT MATTERS

Because identity is known top-down, useState needs no key, there's a place to hang useEffect, and a component is transparent in the native tree (adds identity, not a view). Everything else on this page rests on this.

Verified in the real core: two identical components with no keys → independent state; a tap emits only the one changed line (P|app.1|count=1). Backward compatible — node ids are unchanged, so existing screens were untouched.

02 · local state implemented · on device

useState — no key, any type

State lives outside the component, reconnected each render by the component's identity (like SwiftUI's @State). One function handles every type; you never edit core to store a new one.

The hard test — state follows the item across a reorder (what React/Flutter/SwiftUI need keys for). Tap b twice, then reorder the whole list:

chuks run  VM
tap b twice   → a:0  b:2  c:0
REORDER c,b,a → c:0  b:2  a:0
tap a         → c:0  b:2  a:1
native AOT binary  AOT
tap b twice   → a:0  b:2  c:0
REORDER c,b,a → c:0  b:2  a:0
tap a         → c:0  b:2  a:1
b stays 2 wherever it moves. Also live in the app: the Kit tab's switch/chips and the Login form draft fields run on useState — confirmed rendering + holding state on the iOS simulator.

03 · lifecycle implemented · verified

useEffect — mount, deps, cleanup

The lazy model finally gives lifecycle a home: the framework controls when a component enters and leaves the tree. useEffect(fn, deps) runs after the render commits — on mount, and whenever a value in deps changes. fn returns an optional cleanup that runs before a re-run and on unmount.

lifecycle trace  VM
mount   → MOUNT  ·  v → 0
tap     → v → 1        (mount fx not re-run)
tap     → v → 2
unmount → CLEANUP
lifecycle trace  AOT
mount   → MOUNT  ·  v → 0
tap     → v → 1        (mount fx not re-run)
tap     → v → 2
unmount → CLEANUP
Correct React semantics: the [] effect fires once and cleans up on unmount; the [v] effect re-fires only when v changes. Effects are keyed by identity + their own slot counter, so they never interfere with useState. runEffects() runs after each render; hookSweep() runs cleanups for unmounted components.

04 · two component styles implemented · on device

Function or class — your choice

Both go through one unified render() path in the reconciler. A function is placed with Comp(fn); a class is placed directly with new (honest for a class — functions don't use new). Class components carry props as plain constructor args.

Class components are back because the two AOT bugs that forced functions are both fixed: base-typed virtual dispatch (through any/slice/map) and subclass-in-a-base-slice (the compiler fix committed this session). Proven on device: the Kit gallery places new Toolbar() × 2, each with independent state.

05 · global state implemented · on device

The store — one, or many

For state shared across screens — but with none of Redux's boilerplate. No actions, no reducer, no immutable rebuilds: the reconciler diffs the rendered view, not state references, so a store function just mutates state directly and the framework re-renders. This is the Zustand model, and it's the whole store — plain state + functions, one file.

And unlike Redux (single store by rule), you can spin up as many as you want (the Zustand model) with a generic Store — new Store(initial, reducer) — verified independent:

06 · lazy off-screen assessed · not needed

The work the eager model already avoids

The plan flagged "skip off-screen work." On inspection, the expensive off-screen work is already skipped — and skipping the rest isn't feasible or worthwhile. So this was closed, not built.

SCROLL LISTS

Already virtualized. List builds only the on-screen window (rows r0..r1 from the viewport). Off-screen rows are never built or diffed.

ROUTES & TABS

Already gated. NavStack renders only the current route; TabView renders only the active tab. Background screens don't run.

ARBITRARY COMPS

Not feasible. Yoga does layout on the native side, so the reconciler doesn't know a component's pixel position — it can't tell what's off-screen (except in a List, from rowHeight).

Verdict: the residual eager work is a screen's bounded non-list content (a header, a few cards) — cheap to rebuild + diff, and exactly what React/Flutter/SwiftUI do too. For many repeated items, the answer is already List. No new machinery earns its keep here.

07 · the research it's built on

Same machine as RN, Flutter, SwiftUI

All three share one architecture: an ephemeral description on top, a durable instance underneath holding state, reconnected by identity = (type, position, key). Chuks now matches it.

The one thing Chuks skips: selector/memoization machinery. The others need it to narrow what re-runs; here the runtime re-renders the visible tree and the reconciler diffs, so a plain getState() / useState read is both correct and fast.
